# DRG 医保知识库 + 长期记忆 Agent

一个能跑、有量化评估的对话式 Agent：**查医保 DRG 政策条文**，同时**记住用户说过的事**。

- 问政策问题时，模型会调用 `search_drg_knowledge` 从本地知识库检索条文，带证据等级作答；
- 每轮对话后，一个「记忆抽取器」判断这句话里有没有值得长期保存的用户事实（如「用户在长沙」「下周三有面试」），
  打分过阈值才写进记忆库，下一轮再按当前问题召回并拼进系统提示词；
- 会话历史落在 sqlite，进程重启后同一个 `thread_id` 能接着聊；
- 对外是 HTTP 服务（FastAPI），另有命令行入口。

> **项目状态**：范围已收敛，功能完整、可演示、已知限制逐条列在 [第七节](#七已知限制)。
> `drills/` 和 `notebooks/` 是练习与学习文件，不属于应用代码。

---

## 一、做了什么

| 能力 | 实现 | 量化结果 |
| --- | --- | --- |
| 政策问答（RAG） | Chroma 知识库 + `search_drg_knowledge` 工具，返回带相关性分数的条文 | Hit@3 **100%**，Hit@1 **84.6%**（39 条可答用例） |
| 拒答 | 相关性低于阈值时作答会标明「未命中权威条款」 | 阈值 0.76 下准确率 **100%**，不拒答基线 72.2% |
| 长期记忆 | 抽取 → 打分 → 过阈值入库 → 下轮召回 | 118 条用例上，阈值 0.60 时 P 66.7% / R 100% / F1 0.800 |
| 记忆时效 | `valid_until` 到期自动不召回，但记录保留 | 天数由 Python 算，不给模型算 |
| 会话持久 | LangGraph `SqliteSaver` | 重启进程后同一 `thread_id` 可续聊 |
| HTTP 服务 | FastAPI，`/health` + `/chat` | 自动生成 `/docs` |
| 评测 | 检索 / 拒答 / 记忆入库三套独立评测 | 报告落 `eval/reports/` |

## 二、架构

一次 `POST /chat` 的完整链路：

```
client
  │  POST /chat  { "message": "...", "thread_id": "default_user" }
  ▼
app/api.py
  │  ① 召回：Chroma 记忆库.search(user_id=thread_id, query=message)
  │  ② invoke：config.thread_id + messages=[本轮输入] + memory_block=召回结果
  │        ▼
  │     LangGraph agent（deepseek-flash）
  │        ├─ 政策问题 → 调用 search_drg_knowledge → Chroma 知识库（只读）
  │        └─ 每步状态 → SqliteSaver → data/checkpoints.sqlite
  │  ③ 取最后一条 AI 消息作 answer；从本轮 ToolMessage 里切出知识库原文作 sources
  │  ④ 返回响应之后，BackgroundTasks 触发记忆抽取（第二次模型调用）
  │        → compute_score → 过阈值 → 写入 Chroma 记忆库
  ▼
{ "answer": "...", "sources": [...], "memory_hits": 3, "elapsed": 4.47 }
```

### 两条存储，分工不要混

| 存储 | 位置 | 存什么 | 谁在写 |
| --- | --- | --- | --- |
| **会话历史**（checkpoint） | `data/checkpoints.sqlite` | 每一轮的原话（Human / AI 消息） | LangGraph `SqliteSaver` |
| **长期记忆** | `data/chroma/memory_db` | 抽取出来的用户事实 + 元数据（有效期、主体） | 每轮响应后的后台任务 |

一句话区分：**sqlite 记的是「你说过什么话」，Chroma 记的是「你是个什么人」。**

知识库 `data/chroma/knowledge_db`（只读，由 `scripts/ingest_knowledge.py` 一次性生成）是第三个库，
和上面两个互不相干。

## 四、跑起来

环境：Windows / Python 3.13 / conda env `langchain1.2`（版本见 `requirements.txt`）。

```powershell
conda activate langchain1.2
cd <项目根目录>

# 1) 依赖
pip install -r requirements.txt

# 2) 密钥：项目根目录建一个 .env（4 个值，见 .env.example）
copy .env.example .env

# 3) 建知识库（只有第一次或重建时需要；data/raw 里的语料 → Chroma）
python -m scripts.ingest_knowledge

# 4a) 命令行对话
python -m app.main

# 4b) 或者起 HTTP 服务，浏览器打开 http://127.0.0.1:8000/docs 直接点着试
python -m uvicorn app.api:app --port 8000
```

`.env` 需要四个值：

| 变量 | 用途 |
| --- | --- |
| `DEEPSEEK_BASE_URL` / `DEEPSEEK_API_KEY` | 对话模型（DeepSeek，OpenAI 兼容接口） |
| `PROXY_BASE_URL` / `PROXY_API_KEY` | 向量模型（`text-embedding-v3`，OpenAI 兼容接口） |

> ⚠️ 用 `python -m 包.模块`，不要用 `python app\main.py`。前者把项目根目录放进 `import` 搜索路径，
> `from app.xxx import ...` 才能找到；后者会报 `ModuleNotFoundError: No module named 'app'`。
> `uvicorn` 同理：必须站在项目根目录下启动。

## 五、HTTP 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/health` | 存活探针。不碰向量库、不调模型，可高频调用 |
| POST | `/chat` | 问一轮，同步返回完整答案 |

请求：

```json
{ "message": "不稳定病组怎么定义", "thread_id": "default_user" }
```

响应：

```json
{
  "answer": "……组内病例数 ≤ 10 例的病组被定义为不稳定病组……",
  "sources": ["[证据等级：中｜相关性：0.736] 内容: ……"],
  "memory_hits": 3,
  "thread_id": "default_user",
  "elapsed": 4.47
}
```

- `sources` 是**这一轮**知识库检索到的原文块。用户在聊别的事时它是空数组。
- `thread_id` 是会话身份：同一个 id 共享聊天历史和记忆，换一个就是全新会话。
- `memory_hits` 是本轮召回了几条长期记忆。

## 六、评测

三套评测互相独立，都能复现，`eval/README.md` 里有方法论和口径说明。

```powershell
python -m eval.run_retrieval           # 检索（只做 embedding，不花生成的钱）
python -m eval.run_memory_threshold    # 记忆入库阈值（默认用标注结果，不花 API 钱）
python -m scripts.check_memory_v2      # 记忆模块纯函数断言
```

报告自动写入 `eval/reports/`，文件名带时间戳，可以对比改动前后。

### 检索（54 条用例：39 可答 / 15 不可答，K=5）

| 分组 | 条数 | Hit@1 | Hit@3 | MRR |
| --- | --- | --- | --- | --- |
| 可答·原文问法 | 25 | 92.0% | 100% | 0.960 |
| 可答·口语改写 | 14 | 71.4% | 100% | 0.845 |
| **可答合计** | **39** | **84.6%** | **100%** | **0.919** |
| 不可答·完全跑题 | 7 | — | — | top1 相似度均值 0.416 |
| 不可答·同领域无答案 | 8 | — | — | top1 相似度均值 0.626 |

两个结论：**召回不是瓶颈**（Hit@3 100%），**排序是瓶颈**（口语改写 Hit@1 掉到 71.4%，是混合检索/rerank 的用武之地）。

### 拒答阈值

| 指标 | 数值 |
| --- | --- |
| 不拒答硬答的基线准确率 | 72.2% |
| 阈值 0.54（只看完全跑题） | 100% |
| 阈值 0.76（含「同领域但库里没有」） | 100% |
| 可用阈值区间 | **[0.746, 0.798]，宽度仅 0.052** |

区间这么窄，说明阈值只能当第一道闸，不能是唯一手段。

### 记忆入库（118 条用例）

| 阈值 | 精确率 | 召回率 | F1 | 误存 / 漏存 |
| --- | --- | --- | --- | --- |
| 0.60（当前使用） | 66.7% | 100% | 0.800 | 24 / 0 |
| 0.72 | 77.2% | 91.7% | 0.838 | 13 / 4 |
| 0.84 | 84.3% | 89.6% | 0.869 | 8 / 5 |

F1 最高的区间在 0.78–0.84（≈0.869），代价是漏存从 0 条涨到 5 条。**没有换**，理由见下。

**扩用例的代价，比任何单个分数都值得记**：这套评测早期只有 22 条用例，当时 0.60 的精确率是
93.3%、F1 0.966。把用例扩到 118 条之后掉到 0.80 —— 不是代码变差了，是**小样本给了虚假的信心**。
所以这里贴的是现在的数字，不是当时好看的那一组。

当前 0.60 偏松（24 条误存、0 条漏存）。当初故意选偏松的一侧，是因为误存只是让模型多知道
一件没必要知道的事，漏存会让它忘掉真正重要的事。

#### 那 24 条"误存"到底是什么

逐条看完之后，它们不是同一种东西：

| 原因 | 条数 | 说明 |
| --- | --- | --- |
| 标注与实现版本错位 | **23** | 全部是 `durability ≠ permanent` 的样本。这批标注做于 `valid_until` 出现**之前**，当时的规则是"非永久的一律不记"；现在这类记忆由 `valid_until` 管生命周期，"记下来、到期不召回"才是正确答案。 |
| 地板分边界样本 | 1 | `我有点困`，恰好 0.600。"明说 + 关于本人"就有 0.40 底分，加 `temporary` + `low` 正好压线。 |

（原本还有第 3 类：2 条 PII 漏网 —— 工号和家庭详细住址 —— 已于 2026-11-19 补正则拦掉，
误存从 26 条降到 24 条，见第七节第 13 条。）

所以 **66.7% 这个数主要反映"标注与实现不是同一个版本"，不能当模型能力看**。它真正说明的是：
这批用例必须先按新 schema 重标（补 `subject` / `valid_until` 两个字段，并按新规则重新判 `should_store`），
否则测出来的只是"新实现 vs 旧标准"的错位。

这也是我没有去调阈值的直接原因——**在错的标尺上调参，只会把错标尺拟合得更准**。

**权重校准过一次，结论是「别调」**：在 96 条二次标注上对 1771 组权重做网格搜索，有 677 组（38.2%）
并列最优，且最优解在语义上很荒谬（`user_specific` 0.9、`durability` 0.05）。这叫「数据定不住权重」，
不是「找到了更好的权重」。所以权重保持专家先验不动，等标注量上去再说。

### 诚实的口径

- 检索用例的 `gold_id` 来自库里真实文档的 id，客观可查，谁跑都是这四个数。
- **记忆用例的 `should_store` 判断是 AI 按字段语义拟定的**，所有记忆指标都建立在它成立的前提上。
  所以那组数字衡量的是「评分函数与标注的一致性」，不是「绝对正确」。
- 记忆用例的标注质量是当前最大的不确定项：118 条用例里 `subject` / `valid_until` 字段一条都没有，
  评测因此测不到 v2 的两个新维度。下一步该做的是按新 schema 重标，而不是继续调阈值。
- 评测只覆盖**检索层**。「tool 被调用之后，模型有没有把低质量结果当成权威条款」这一层还没测。

## 七、已知限制

按「会不会被问倒」排序，全部如实列出：

| # | 限制 | 影响 | 打算怎么修 |
| --- | --- | --- | --- |
| 1 | `api.py` 用一把锁串行化对话（`_db_lock`） | 并发度 = 1，两个用户也得排队 | 按会话分库 / 换支持并发写的后端 |
| 2 | 记忆抽取挂在 `BackgroundTasks`，没有重试和持久化 | 响应发出后进程崩了，这轮记忆就丢 | 换成真正的任务队列 |
| 3 | 记忆延迟一轮生效 | 这轮说的话，这轮的回答里还没变成「记忆」 | 设计取舍，不打算改 |
| 4 | 无鉴权，`thread_id` 明文 | 知道 id 就能续上别人的会话 | 上登录 + 会话所有权校验 |
| 5 | `sources` 依赖工具输出的 `[证据等级` 前缀 | 改工具文案要同步改 `api.py` | 让工具返回结构化对象 |
| 6 | 没有历史裁剪 | 长会话 token 线性增长 | 暂不痛（记忆不占历史），需要时再加 |
| 7 | `similarity_search_with_score` 返回的是**距离**不是相似度 | 变量名叫 `score`，容易误读 | 改名或转换 |
| 8 | upsert 会刷新 `created_at`；同一批里 `key` 重复时后者覆盖前者 | 时间信息不准 / 静默丢一条 | 补唯一性校验 |
| 9 | 模型会把 `[有效期至 2027-01-31，还剩 82 天]` 误读成用户的计划期限 | 语义错误 | 给的不是日期而是语义（如「这条记忆到 X 失效」） |
| 10 | 没有 pytest、没有 CI | 回归靠手工脚本 | `scripts/check_memory_v2.py` 先顶上 |
| 11 | 向量库约 55MB，不入版本库 | 克隆后必须重跑 `ingest_knowledge` | 已有文档说明 |
| 12 | 未实现流式输出 | 用户要等全文生成完 | 见下 |
| 13 | 敏感信息正则只覆盖身份证 / 手机号 / 银行卡 / 凭据关键词 → **2026-11-19 已修** | 工号（`A20230149`）、家庭详细住址曾以满分入库 | 已补 3 条正则，并加反例测试确认「室友」不被误伤；误存 26 → 24 |

## 八、作者本人自述

### 8.1 为什么做这个项目

我开始做的时候没想"赛道"，只想找一个**能自己验证对错**的题目。

Coding Agent 我看过，但一个人做很难做出差异，更麻烦的是**没法判断自己做得对不对**：代码能不能跑、跑得好不好，
标准太模糊。RAG 不一样——答案对不对，可以拿原文逐条比对。

选医保 DRG 是顺着这个思路：我在网上找到一份清洗好的医保问答数据集（`data/raw/`，Alpaca 格式的
`instruction` / `output` 字段），它本身就是"一问一答"的条款形态。这意味着我可以给每条测试用例标一个
`gold_id`（这道题该命中库里哪条文档），然后完全自动地算"该找到的有没有找到"，
不需要人读答案，也不需要另一个模型当裁判。

所以这个项目真正的起点是：**先确认这个题目能被测量，再动手写代码。**
`eval/` 不是做完补的，是选题时就定下的前提。


### 8.2 最难的一处 / 最大的收获

**最难的：给"该不该记住"这件事定边界**

最初我以为这是个调参问题：给 4 个维度分配权重，再定一个阈值就行，所以第一次是拍脑袋定的。
后来我把这件事拆成两步，才想清楚为什么调参没用：

1. **闸门**（硬规则，一票否决）：一次性请求、不关于用户本人、敏感信息，直接 0 分，不参与加权。
2. **加权**（在"都该存"的样本里排序）：`durability` 0.40 / `explicitness` 0.25 / `action_relevance` 0.20 / `user_specific` 0.15。

**最大的收获：承认"分数管不了所有事"**

我跑了 1771 组权重的网格搜索，又做了 ±0.10 的敏感度分析。结论很反直觉：

- 有 **677 组（38.2%）并列最优** —— 这批标注根本"定不住"权重，选哪组都说得通；
- 网格最优解在语义上很荒谬（`user_specific` 0.9、`durability` 0.05），说明"F1 最优 ≠ 合理"；
- 而且换一批用例，最优区间就变了：96 条那批和 118 条那批给出的答案不一样。

于是我停手了，没改权重。转而承认一件事：**有些判断根本不在"分数"这个维度里。**
"我妹妹今年高考"该不该存，取决于**主体是谁**；"下个月面试"该不该留，取决于**日期**。
这两件事用多少个权重都表达不出来。

所以我在底层加了两个**不参与打分**的字段：`subject`（区分用户本人 / 具体他人）和
`valid_until`（到期不再召回，但不删除），把系统拆成两条轨道：**score 管准入，metadata 管可见性**。

另一处是真踩过坑才加的：手机号、身份证、银行卡这类内容**分数会是满分**——它们通常"明说 + 关于本人 + 影响决策"三样全占。
阈值救不了它，所以必须在打分之前用正则硬拦（`passes_gate` 里的 `_SENSITIVE_PATTERNS`）。

但这一层一开始并不全：我后来逐条查误存时才发现，**工号和家庭详细住址都没被拦住**（正则只覆盖了四类）。
补上之后误存从 26 条掉到 24 条。剩下这 24 条里，23 条是"标注与实现版本错位"，1 条是地板分边界——
都不是这一层能解决的。

> 标注我说清楚：记忆用例那 118 条 "should_store" 是 **AI 按字段语义拟的，不是人工标的**。
> 所以我只把它当"看方向"的依据，没当成"准确率"用。这句在 `eval/README.md` 里也写着。



### 8.3 如果重做一遍，会改什么

**第一件：先做评测，再调参数——这次我是反过来做的。**

现在的记忆入库阈值是 0.60，在 118 条用例上是精确率 66.7%、24 条误存、0 条漏存。
但我不敢动这个阈值，原因有两层。

第一层：那 118 条标注是 **AI 按字段语义拟的**，而且是在 `subject` / `valid_until` 出现之前拟的。
逐条查完这 24 条误存，23 条属于"标注与实现版本错位"——当时规则是非永久一律不记，
现在这类记忆该记、到期不召回；另外 1 条是地板分边界。
（原本还有 2 条 PII 漏网，已经补正则修掉了。）
这种情况下调阈值，等于拿错的标尺量自己。

第二层：这 118 条用例里**根本没有** `subject` / `valid_until` 字段，评测脚本也用不到它们。
也就是说 v2 那两个维度从来没被测过。

所以第一件事会是：**人工把这 118 条过一遍**，把标错的挑出来。标注可信之后，阈值才有讨论的价值。
这也是我最后没动权重的同一个理由——数据定不住的东西，不要用手调去补。

**第二件：并发。** 现在 `api.py` 里一把 `threading.Lock` 把所有对话串起来，单轮约 4 秒，
100 个并发用户就得排队五分钟以上。这是"能演示"和"能上线"之间最明显的一条沟。
重做的话会一开始就按会话分库（或直接换支持并发写的 Postgres），而不是最后加一把锁把问题盖住。

**第三件：一个我只有想法、没动过代码的方向。** 现在低置信度时走的是"证据等级三档 + 强制降级声明"：
命中率低就让模型先声明"未命中权威条款"，再谈通用知识。这守住了合规底线，但用户体感是被推走——
强答有误导风险，过度拒答又显得没用。我倾向的做法是**两层库 + 意图路由**：官方条款库保持严格，
另外建一个小而短的 FAQ 库专门接常识性提问，进检索前先判断这句话属于哪一类。
不过这条只是方向，我不会把它写成"已完成"。

## 九、附录：这个项目是怎么长出来的

项目原本是一个平铺的 `model/` 目录（`llm.py`、`memory.py`、`database.py`、`tool.py`、`demo.py`……），
后来重构成按职责分层的 `app/` 结构。业务逻辑没有改动，只改了 import 路径和写死的相对路径。

| 原文件 | 现在的位置 |
| --- | --- |
| `llm.py` | `app/agents/chat_agent.py` |
| `memory.py` | `app/memory/models.py` |
| `embeddings.py` | `app/memory/store.py` |
| `database.py` | `app/knowledge/database.py` |
| `tool.py` | `app/tools/builtin_tools.py` |
| `demo.py` | `app/main.py` |
| `vector_sql.py` | `scripts/ingest_knowledge.py` |
| `chroma_*/` | `data/chroma/` |

重构后的关键一步：所有路径集中到 `app/config.py`，不再写 `"./chroma_knowledge_db"` 这种
依赖「当前工作目录」的相对路径——这样在哪个目录下运行都是对的。

之后逐步补齐的四件事：记忆 upsert、记忆时效（`valid_until` + 天数标注）、
会话持久化（`SqliteSaver` 替换内存版 `MemorySaver`）、HTTP 服务化（FastAPI）。
