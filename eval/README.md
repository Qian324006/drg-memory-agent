# eval/ —— 评测套件

只做测量，不改 `app/` 里任何业务代码。它 import `app` 的向量库和评分函数，跑一遍，出数字。

## 为什么不需要你人工判断「回答对不对」

要分两层看，别混：

| 层 | 能不能全自动 | 怎么做到 |
| --- | --- | --- |
| **检索层**：该找到的条款，找到没有？ | ✅ 完全自动 | 每条用例自带 `gold_id`（这条问题对应库里哪条文档的 id）。只要看这个 id 有没有进前 K 名，就是 0/1，不需要人读答案 |
| **答案层**：模型生成的回答，内容对不对？ | ❌ 不能全自动 | 要么人标答案，要么让另一个 LLM 当裁判（有成本、有偏差）。留到服务化之后再做 |

**先把检索层测了**，因为 RAG 出问题十有八九是「没召回正确材料」，而不是「模型不会总结」。这层免费、可复现、不用人工，性价比最高。

`gold_id` 不是我猜的：用例是从你库里 `drg_qa_*` 的真实文档反查出来的，id 与文档一一对应。

## 用法

```powershell
cd D:\langchain1.2_toturial\model\drg_memory_agent

# 检索评测（不花 API 钱：只做 embedding，不做生成）
python -m eval.run_retrieval

# 记忆阈值评测（默认用标注好的抽取结果，不花 API 钱）
python -m eval.run_memory_threshold

# 想测「真实抽取器」的表现（会调用 22 次 API）
python -m eval.run_memory_threshold --extractor llm
```

报告自动写到 `eval/reports/`，每次带时间戳，可以对比改动前后的差异。

## 当前基线（2026-10-30，54 条检索用例 + 22 条记忆用例）

### 检索

| 分组 | 条数 | Hit@1 | Hit@3 | top1 相似度均值 |
| --- | --- | --- | --- | --- |
| 可答·原文问法 | 25 | 92.0% | 100% | 0.921 |
| 可答·口语改写 | 14 | 71.4% | 100% | 0.861 |
| 可答合计 | 39 | 84.6% | 100% | 0.899 |
| 不可答·完全跑题 | 7 | - | - | 0.416 |
| 不可答·同领域无答案 | 8 | - | - | 0.626 |

**三个可以直接用的结论：**

1. **召回不是瓶颈**：Hit@3 = 100%，说明只要问题口语化程度不高，正确材料一定能进前 3。
2. **排序是瓶颈**：Hit@1 从 92%（原文）掉到 71.4%（口语改写）。→ 混合检索 / rerank 有用武之地，且能给出「Hit@1 从 84.6% 涨到 X%」的对比。
3. **检索层没有「证据等级」概念**：`search_drg_knowledge` 只在 `if not docs` 时拒答，而 k=3 永远有结果，
   所以只要 tool 被调用，无论检索质量多差都会返回 3 条条款。

> ⚠️ **口径纠正（2026-10-30）**：这条结论之前被写成「拒答率 0%」，那是**错的**。
> 完整链路是「agent 的 LLM 先决定调不调 tool」，领域外的问题通常根本不会走到检索，
> 而是由模型用自身知识回答。本评测只测**检索层**，不能代表产品层的拒答行为。
> 真正要测的是「tool 被调用后，模型有没有把低质量检索结果当成权威条款」——
> 那需要一个跑完整 agent、记录 `tool_calls` 的评测（尚未实现）。
> 但这个纠正**没有让问题消失，反而让问题更清楚**：没有证据分级时，
> 「领域内但库里没有」的问题会被模型用自己的知识答得像官方条款。

#### 历史结果（22 条用例，2026-10-30）

2026-10-30 在 `app/memory/models.py` 里加了硬规则闸门（一次性请求 / 不关于本人 / 敏感信息 直接 0 分），
下面是在这之后的结果：

| 阈值 | 精确率 | 召回率 | F1 | 误存 |
| --- | --- | --- | --- | --- |
| 0.60（当前） | 93.3% | 100% | 0.966 | 1 |
| **0.62（最优）** | 100% | 100% | **1.000** | 0 |

加闸门之前是 87.5% / 100% / 0.933（同一批用例的旧版本）。多出来的两处误存（身份证、手机号）
已被闸门拦掉——**它们本来就不是阈值能解决的问题**，分数是满分 1.0。

剩下那 1 条误存是「我有点困」（恰好 0.600）：这说明线性加权有个「地板分」——
只要「明说 + 关于本人」就有 0.25 + 0.15 = 0.40 底分，再加 temporary + low 正好卡在阈值上。
**这不是调某个权重能解决的**，详见 `eval/calibrate_weights.py` 的输出。

### 权重有没有依据

跑 `python -m eval.calibrate_weights`，它做三件事：拆解边界样本的分数、在权重单纯形上网格搜索、
对当前权重做 ±0.10 敏感度分析。当前结论：

- 当前权重在 0.64 阈值下 F1 = 1.000，±0.10 扰动下 F1 波动 < 0.05（不敏感）；
- **但 1771 组权重里有 677 组（38.2%）并列最优** → 这批标注「定不住」权重，选哪组都主观；
- 网格最优解在语义上很荒谬（user_specific 0.9、durability 0.05），说明「F1 最优 ≠ 合理」；
- 结论：权重保持专家先验不动，先扩标注到 **60–80 条**再校准。

## ⚠️ 关于标签的诚信说明

- 检索用例的 `gold_id` 来自你库里真实文档，客观可查。
- **记忆用例的 21 条 `should_store` 判断是 AI 拟的**（按你 `compute_score` 的字段语义 + 常识）。上面所有记忆指标都建立在它还成立的前提上。
- 所以：**引用这些数字前，先把 `cases_memory.jsonl` 逐条看一遍**，不同意就改 `should_store`，然后重跑。数字会变，但那就是你自己的结论，面试时才敢讲。

## 下一步怎么把它用在优化上

改检索方案时（比如加 BM25 混合检索），只需要改 `run_retrieval.py` 里的 `retrieve()`：

```python
def retrieve(query, k):
    # 现在：纯向量
    # 之后：BM25 + 向量 -> EnsembleRetriever，或者加 reranker
    ...
    return ids, distances   # 保持返回「id 列表 + 分数列表」即可
```

`run_retrieval.py` 的统计、报告、逐条明细都不用动。这就是评测和实现解耦的意义。

## 用例怎么扩

- `cases_retrieval.jsonl` 一行一条：`{"id","kind","question","gold_id"}`
  - `kind` 决定分组：`answerable_verbatim` / `answerable_paraphrase` / `unanswerable_off_topic` / `unanswerable_near_domain`
  - 不可答用例 `gold_id` 写 `null`
- `cases_memory.jsonl` 一行一条，需要给出「理想的抽取结果」的每个字段，脚本才能算分。

用例越多结论越稳。现在 54 + 21 条只够「看出方向」，不够「下结论」——面试时如实说「样本不大，是初步结论」比吹成定论安全。
